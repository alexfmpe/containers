Should be extendable to the `Map` equivalents and to `Map`/`Set` mixes like `restrictKeys`, but I wanted to first get feedback on this very debatable change.

The implementations here grab the root of one tree as a proxy for median value, then find its place in the other tree to split that one as well so that the problem is divided into two smaller ones on smaller tree pairs.
This has the advantage that it's highly parallelizable.
However, I don't think we're actually leveraging that?
Seems to me that always doubling parallelism on every layer would backfire from contention and overhead so we'd need to require/choose a tree size/depth cutoff and also take `numCapabilities` or so into account.

Given we can convert to/from lists in linear time, and that we can merge two ordered sequences in linear time, I had a go at the single threaded friendly implementation for `Set`.
